# Как работаем с GitHub в «Нефтянке»

Ребят, здесь наши правила работы с [репозиторием проекта](https://github.com/A-m-u-r/neft). Они относятся к коду, описаниям процессов, схемам и другим файлам.

Задачи ведём в YouGile, а файлы и историю изменений храним на GitHub. Для каждой задачи создаём свою ветку и отправляем результат на проверку через Pull request. В общую версию добавляем работу после одобрения другого участника.

## Порядок работы

**Задача → свежий `main` → своя ветка → изменения → commit → push → Pull request → проверка → merge в `main`.**

Такой порядок называется [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow). Ниже разбираем его на нашей задаче.

### 1. Берём задачу и создаём ветку

Открываем свою задачу в YouGile, читаем описание и переносим её в «В работе». Если собираемся менять те же файлы, что и другой человек, заранее договариваемся в чате задачи.

На компьютере переключаемся на `main` и получаем последние изменения с GitHub. `main` хранит общую принятую версию проекта. От неё создаём новую ветку, то есть отдельное место для своей работы. Например, для пользовательских сценариев в задаче NEF-12: `nef-12-user-stories`.

Называем ветки по задаче, латиницей, без пробелов. Если имя уже задано в задаче, используем его. Обычный порядок: одна задача, одна ветка, один Pull request. Несвязанные изменения выносим в отдельную задачу.

Ветки позволяют готовить изменения до добавления в общий проект. [Пример создания ветки](https://docs.github.com/en/get-started/using-github/hello-world#step-2-create-a-branch)

### 2. Меняем файлы и делаем commits

Здесь три разных действия:

| Действие | Что происходит при работе на компьютере |
| --- | --- |
| Сохранить файл | Редактор записывает изменения в файл. |
| Сделать commit | Git фиксирует выбранные изменения в истории нашей ветки на компьютере. |
| Сделать push | Наши commits отправляются на GitHub и становятся доступны команде. |

Перед commit смотрим список изменённых файлов и сами изменения. Выбираем только то, что относится к этой порции работы. Один commit может включать несколько файлов.

Сохраняем осмысленными порциями и пишем, что сделали. В задаче NEF-12 могут постепенно появиться такие commits:

```text
Добавил список пользовательских сценариев
Описал сценарии загрузки и просмотра данных
Добавил критерии приёмки
```

Название «Изменения» ничего не объясняет. По сообщению человек должен понять, что изменилось, даже через месяц.

В GitHub Desktop выбираем файлы, заполняем **Summary** и нажимаем **Commit to имя-ветки**. Затем отправляем работу кнопкой **Push origin**. Для новой ветки сначала может появиться [**Publish branch**](https://docs.github.com/en/desktop/making-changes-in-a-branch/managing-branches-in-github-desktop#publishing-a-branch). Несколько commits можно отправить одним push. [Инструкция по commits и push](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop)

Если редактируем файл прямо на сайте GitHub, commit уже сохраняется на GitHub: отдельного push для него нет. Всё равно работаем в своей ветке. [Редактирование на сайте](https://docs.github.com/en/get-started/using-github/hello-world#step-3-make-and-commit-changes)

### 3. Отправляем работу на проверку

Перед отправкой сами проверяем результат. Код запускаем и проверяем затронутый сценарий. Документы перечитываем, открываем схемы, проверяем ссылки. Если что-то проверить не получилось, прямо пишем об этом.

На GitHub открываем **Pull requests → New pull request**. Выбираем `base: main`, а в `compare` свою ветку. Pull request, или PR, это предложение добавить наши изменения в общую версию.

В описании пишем:

```text
Задача: ссылка на задачу в YouGile
Что сделал: ...
Как проверил: ...
Вопросы или ограничения: ... (если есть)
```

Просим другого участника проверить работу. Ссылку на PR прикрепляем в YouGile и переносим задачу в «На проверке».

Проверяющий смотрит, решена ли задача, понятен ли результат и работает ли изменённая часть. Замечания пишет в PR, а после проверки ставит **Approve**. [Как устроена проверка Pull request](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)

### 4. Исправляем замечания и добавляем результат в `main`

Поправки делаем в той же ветке: меняем файлы, создаём новый commit и делаем push. Открытый PR обновится автоматически. После исправлений просим посмотреть работу ещё раз.

Когда другой участник одобрил результат и замечания закрыты, объединяем PR с `main`. Это называется **merge**. Завершённую ветку можно удалить: принятые изменения останутся в `main`, а история сохранится. [Объединение PR](https://docs.github.com/en/get-started/using-github/hello-world#step-5-merge-your-pull-request)

После принятия результата переносим задачу в «Готово». Для следующей задачи снова переключаемся на `main`, получаем последние изменения и создаём новую ветку.

## Что не загружаем и когда спрашиваем

Репозиторий открытый, файлы видны всем. Не отправляем пароли, ключи доступа, файлы `.env`, личные данные, реальные данные заказчика и закрытые документы, включая КП. Для примеров используем выдуманные данные. Перед commit и push просматриваем файлы, даже если настроен `.gitignore`.

Если секрет уже попал на GitHub, сразу сообщаем руководителю. Простое удаление файла оставит его в истории; ключ или пароль нужно отозвать либо заменить. [Что делать с опубликованными секретами](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

Если возник конфликт, Git не смог автоматически совместить изменения. Сохраняем чужую работу и разбираемся вместе с её автором. При непонятной ошибке присылаем её текст и рассказываем, что делали. Команды, которые удаляют файлы или переписывают общую историю, наугад не запускаем.

## Как подтвердить ознакомление

Прочитайте инструкцию и напишите **«ознакомился»** в чате общей задачи в YouGile. Если что-то непонятно, спрашивайте там же. Общую задачу закроем, когда ответят все.
